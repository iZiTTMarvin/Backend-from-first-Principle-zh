第一部分 / 基础

## HTTP 的核心原理

HTTP（超文本传输协议）是一种**应用层协议**：位于 OSI 模型的第 7 层，用于传输超媒体，以及——对我们来说同样重要的——以编程方式访问 API 和进行机器间通信。「应用层」意味着它是最顶层，是定义消息_含义_的那一层（这是一个对 `/users/5` 的 GET 请求），而不是定义字节如何在线缆上物理移动的那一层。作为后端工程师，我们几乎完全生活在这里；下面的各层（TCP 段、IP 包、以太网帧）都被抽象为「一根可靠的管道」。HTTP 的核心有两个理念。

### 1. 无状态

服务器在**两个请求之间不保留任何会话记忆**。每个请求都是完全自包含的：它必须携带服务器处理它所需的一切——认证令牌、Cookie、目标资源、方法、任何偏好设置。服务器一旦完成响应，就会丢弃关于该请求的所有认知。同一客户端在一毫秒后发来的第二个请求，会被当作一个全新的、完全无关的事件来对待。这个协议在设计上就是健忘的。

每个请求都像一封信，每一次都必须重新介绍你是谁——邮政系统从不记得你的上一个信封，所以每封信都必须重新写明寄件人、收件人和回信地址。

#### 为什么无状态是刻意的特性，而不是缺陷

让服务器「记住」你似乎更简单。选择无状态，恰恰是因为「遗忘」换来了三个在规模化场景下极其重要的性质：

- **简单性**：服务器不需要在内存中为每个用户分配、跟踪、过期或回收会话状态。每个请求都被独立处理，因此处理逻辑是其输入的纯函数。活动部件越少，bug 越少。
- **水平可扩展性**：因为没有服务器「拥有」某段对话，任何请求都可以被路由到集群中的_任意_一台服务器。负载均衡器可以把一个用户的十个请求分散到十台不同的机器上，每台都能正确处理自己的那个请求，因为每个请求都自带上下文。如果没有无状态，你就需要「粘性会话」把每个用户钉在一台机器上，这既浪费容量，又会在那台机器宕机时崩溃。
- **崩溃韧性**：如果一个节点中途死掉，没有内存中的会话需要重建。客户端只需重试，负载均衡器把它发到别处，什么都不丢。相比之下，有状态的服务器在崩溃时会丢失所有活跃会话。

代价是**连续性必须在每个请求上重建**。由于协议本身会遗忘，我们每次都用 Cookie、服务器端会话或令牌来重新建立身份——随每个请求重新发送一小段凭证，好让服务器能重新查出你是谁。这些状态管理技术在第 8 节详述；这里的关键点是，它们位于无状态协议_之上_，而不是改变它的本性。

### 2. 客户端-服务器模型

通信**总是由客户端发起**：浏览器、移动应用，或另一个后端服务。客户端决定它想要什么，组装出一个完整的请求（URL、方法、请求头、请求体），然后发送。服务器本质上是被动的：它托管资源、监听，并且只在_响应_请求时才说话。在经典 HTTP 中，它不能自发地向没有提出请求的客户端推送数据。这种不对称正是「服务器无法通知浏览器有新消息」这个问题在历史上用轮询来解决的原因，也是 WebSocket 和 Server-Sent Events（第 19 节、第 17 节）存在的意义——当你确实需要服务器推送时，打破严格的请求/响应形态。

### 底下的传输层：为什么是 TCP

HTTP 自己不搬运字节，它把这件事委托给传输协议。它对传输协议只有一条硬性要求：**可靠性**。消息必须完整、有序地到达，否则传输层必须报错——HTTP 无法容忍字节被静默丢弃或乱序，因为只交付了一半的请求头或请求体毫无意义。互联网上两种主流传输协议是 TCP 和 UDP：

- **TCP** 基于连接且可靠：它通过三次握手（SYN -> SYN-ACK -> ACK）建立连接，给每个字节编号、确认接收、重传丢失的数据，并按序交付。HTTP/1 和 HTTP/2 就跑在它上面。
- **UDP** 无连接、「发后即忘」，速度快但没有任何投递保证。原生 HTTP 不能直接使用它，但 HTTP/3 的 QUIC 层在 UDP 之上重建了可靠性（第 2 节）。

TCP 握手和任何 TLS 协商都发生在第 7 层之下，它们是传输/网络工程层面的关注点。我们把它们当作：「一条可靠的、可能加密的管道已经建立，现在请求和响应消息在其上流动。」这个抽象足以推理和调试绝大多数后端行为。

### 给每个方法分类的三个属性

规范中的三个精确术语贯穿本手册，它们决定方法的行为方式、缓存如何对待它们，以及客户端是否可以重试。这里先预览，第 6 节会深入剖析：

- **安全（Safe）**：请求是只读的；发出它不会改变服务器状态（如 GET、HEAD）。爬虫和链接预取器依赖这一点。
- **幂等（Idempotent）**：发出请求一次或 N 次，服务器的最终状态相同（如 GET、PUT、DELETE）。正是这个性质让请求在超时后可以安全重试。
- **可缓存（Cacheable）**：响应可以被存储并复用，以满足之后的等价请求（如 GET、HEAD），省掉一次往返。

每个 HTTP 版本都保持了相同的请求/响应语义，但重做了**底层连接的使用方式**，每一代都在追逐更低的延迟。理解这段演进，就能解释某些性能问题为什么存在，以及现代 HTTP 如何解决它们。

### 每个版本解决的问题

**1.0 的浪费。** 建立 TCP 连接要花费一次往返（握手），然后才有第一个 HTTP 字节流动。对页面上的每张图片、每个脚本和每个样式表都这样做——几十条连接——增加了巨大的延迟。**1.1 的持久连接**通过让一条 TCP 连接复用于多个请求/响应对（第 16 节）解决了这个问题，摊薄了握手成本。

**Host 请求头。** 1.1 把 `Host` 设为强制，这启用了_虚拟主机_：一个 IP 地址、一台服务器可以托管多个域名，按每个请求的 `Host` 请求头来路由。本质上，整个共享主机和反向代理的世界都依赖于此。

**队头阻塞。** 即使有持久连接，HTTP/1.1 在一条连接上也是_串行_处理请求的——响应 2 必须等响应 1 完成才能开始。一个慢响应会堵住排在它后面的一切。**HTTP/2 的多路复用**在应用层解决了这个问题：许多独立的_流_共享一条连接，来自不同流的帧交错传输，慢响应不再阻塞其他响应。HTTP/2 还从冗长的文本切换到了紧凑的**二进制分帧**层，并加入了 **HPACK** 头部压缩（像 Cookie 和 User-Agent 这样重复的头部只发送一次，之后引用），外加_服务器推送_（主动发送客户端将会需要的资源，如今已基本被弃用，改用预加载提示）。

**TCP 自己的队头阻塞。** HTTP/2 在 HTTP 层消除了它，但更深一层的问题还在：因为所有流共享一条 TCP 连接，一个丢失的 TCP 包会堵住_每一条_流，直到它被重传——TCP 保证整个字节流按序交付。**HTTP/3 的 QUIC** 通过跑在 UDP 之上、自己实现按流的可靠性来修复这一点：丢包只阻塞它所属的那条流。QUIC 还把 TLS 握手折叠进了连接建立过程，因此安全连接用更少的往返就能建立（恢复会话时通常为零）。

唯一的要点

跨所有版本，心智模型是相同的：**客户端和服务器建立一条连接，然后消息来回流动。** 各版本只是优化管道工程——连接复用、并行、压缩，以及由哪种传输协议承载这一切。

### 请求消息，逐行拆解

```text title="原始 HTTP 请求"
POST /api/v1/notes HTTP/1.1          # 请求行：方法 / 目标 / 版本
Host: api.example.com                # HTTP/1.1 中强制（虚拟主机）
User-Agent: curl/8.4.0
Authorization: Bearer eyJhbGc...     # 请求头：大小写不敏感的 key: value
Content-Type: application/json       # 消息体是什么
Content-Length: 33                   # 消息体的字节数，告诉服务器它在哪里结束
                                     # 空行：请求头结束，消息体开始
{"title":"buy milk","done":false}    # 请求体
```

**请求行**有三个部分：_方法_（意图，第 6 节）、_请求目标_（通常是路径加可选的查询字符串，如 `/notes?done=false`），以及_协议版本_。**Host** 请求头与目标是分开的，因为一台服务器可能托管多个域名。**Content-Length** 比看起来更重要：在持久连接上，许多消息首尾相接地在流上传输，它告诉接收方在下一条消息开始之前要读多少个字节——搞错了，整条连接就会失步。

### 响应消息

```text title="原始 HTTP 响应"
HTTP/1.1 201 Created                 # 状态行：版本 / 状态码 / 原因短语
Content-Type: application/json
Content-Length: 41
Date: Sat, 30 May 2026 12:00:00 GMT
                                     # 空行
{"id":42,"title":"buy milk","done":false}
```

**状态行**携带版本、客户端据此分支的数字_状态码_（第 10 节），以及一段人类可读的_原因短语_（"Created"、"Not Found"）。原因短语纯粹是信息性的——客户端必须依据数字行动，绝不能依据文本，因为文本会变化，而且在 HTTP/2 中被完全丢弃。

### MIME 类型：`Content-Type` 的词汇表

自 HTTP/1.0 起，同一个协议承载任何类型的内容——JSON、HTML、图片、视频、二进制块。接收方需要知道是哪一种，这就是 `Content-Type` 请求头中 **MIME 类型**（媒体类型）的工作。它的语法是 `type/subtype` 加可选参数：`application/json; charset=utf-8` 或 `multipart/form-data; boundary=----X7`。`charset` 参数告诉解析器文本编码；在文本上省略它可能导致乱码。把 `Content-Type` 写错是常见的 bug：把 JSON 标成 `text/plain` 发送，许多客户端就不会解析它；服务器也可能用 415 Unsupported Media Type 拒绝一个声明类型不被接受的请求体。

| MIME 类型                         | 用途                                                        |
| --------------------------------- | ----------------------------------------------------------- |
| application/json                  | 现代 API 的默认选择。                                       |
| application/x-www-form-urlencoded | 经典 HTML 表单提交，编码为 `key=val&k2=v2`。                |
| multipart/form-data               | 文件上传与混合二进制字段（第 17 节）。                      |
| text/html, text/plain             | 网页与纯文本。                                              |
| application/octet-stream          | 任意的「就是字节」；通常触发文件下载。                      |
| text/event-stream                 | Server-Sent Events 流式推送（第 17 节）。                   |

通用的顺序规则

请求头在状态行和消息体**之前**上线——接收方先读它们，才知道如何解释后面的内容。所以一旦你写入了状态码（Go 的 `w.WriteHeader()`）或开始流式输出消息体，之后再设置的任何请求头都会被静默丢弃：字节已经发出去了。每个框架中的不变量都是**设置请求头 -> 写状态码 -> 写消息体**。忘记它，就是经典的「我的请求头没发出去」bug 的根源。

```go
package main

import (
    "encoding/json"
    "io"
    "net/http"
)

type Note struct {
    ID    int    `json:"id"`
    Title string `json:"title"`
    Done  bool   `json:"done"`
}

func createNote(w http.ResponseWriter, r *http.Request) {
    body, _ := io.ReadAll(r.Body)      // 1. 读取请求体
    defer r.Body.Close()

    var in Note
    if err := json.Unmarshal(body, &in); err != nil {
        http.Error(w, "invalid JSON", http.StatusBadRequest)
        return
    }
    w.Header().Set("Content-Type", "application/json") // 2. 先写请求头
    w.WriteHeader(http.StatusCreated)                  // 3. 状态码
    in.ID = 42
    json.NewEncoder(w).Encode(in)                      // 4. 最后写消息体
}

func main() {
    http.HandleFunc("POST /api/v1/notes", createNote)  // Go 1.22 方法路由
    http.ListenAndServe(":8080", nil)
}
```

## 为什么需要请求头

请求头是附加在请求或响应上的**键值对元数据**，位于起始行和消息体之间。一个自然的问题是：为什么要有单独的一节？为什么不把这些信息放进 URL，或者放进消息体里？

一个待寄的包裹会把收件人、地址和邮编写在_外面的标签_上，而不是封在箱子里。沿途经手的每个快递员一眼就能读到路由信息，无需撕开箱子。如果这些数据在箱子里面，每个经手人都得拆开再重新打包，才能知道它接下来要去哪。HTTP 请求头就是那张外层标签：任何中间方（代理、缓存、网关）无需触碰载荷就能读取并据以行动的元数据。

把元数据与载荷分离，换来了两个基础性质：

- **可扩展性**：新能力只需定义新请求头即可加入，协议结构零改动。安全策略、客户端提示、压缩协商、你自己应用的自定义 `X-` 头、追踪 ID——这些年所有这些都叠加在 HTTP 之上而没有破坏旧客户端，因为任何不认识某个请求头的东西都会直接忽略它。协议在没有版本动荡的情况下生长。
- **远程控制**：请求头让客户端发送引导服务器行为的_指令与偏好_，也让服务器发回指令。客户端说「我想要 JSON」（`Accept`），服务器回复「把这个缓存一小时」（`Cache-Control`），「这是我」（`Authorization`），「我在和这个域名说话」（`Host`）。同一个请求体，仅凭请求头不同就能产生不同的响应——它们是这次交换的旋钮与开关。

请求头的名字还是**大小写不敏感**的、与顺序无关的，这就是框架会把它们规范化的原因。而且因为中间方会读它们，缓存、内容协商、认证和安全策略都通过请求头表达——后面的章节在很大程度上就是一场对具体请求头及其背后机制的巡礼。

## HTTP 请求头的类型

已定义的几百种请求头可以归入几个功能桶。知道属于哪个桶，就知道谁设置它、它管什么。

| 类别     | 用途                                                                   | 示例                                                                                    |
| -------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 请求头   | 由客户端发送；描述客户端、它的能力以及它想要什么                       | `User-Agent`、`Authorization`、`Accept`、`Host`、`Cookie`                               |
| 通用头   | 同时适用于请求和响应；关于消息本身的元数据                             | `Date`、`Connection`、`Cache-Control`                                                   |
| 表示头   | 描述消息体，好让另一方能够解释和处理它                                 | `Content-Type`、`Content-Length`、`Content-Encoding`、`ETag`                            |
| 安全头   | 由服务器发送，控制客户端（浏览器）行为并阻断各类攻击                   | `Strict-Transport-Security`、`Content-Security-Policy`、`X-Frame-Options`、`Set-Cookie` |

安全头值得逐个理解，因为每一个都是针对某种具体的、有名字的攻击的直接对策。它们的工作方式是指示浏览器拒绝危险行为：

- `Strict-Transport-Security`（HSTS）——告诉浏览器「在接下来的 N 秒内，只通过 HTTPS 联系我，即使链接写的是 http\://」。这击败了**协议降级攻击**：网络上的攻击者把连接剥回明文 HTTP 来读取或篡改它。
- `Content-Security-Policy`（CSP）——一份允许列表，规定脚本、样式、图片和其他资源可以从哪里加载（如 `default-src 'self'`）。它的主要工作是化解**跨站脚本（XSS）**：即使攻击者注入了 `<script>` 标签，除非其来源在允许列表上，浏览器也会拒绝执行。
- `X-Frame-Options: DENY`——禁止你的页面被嵌入其他站点的 `<iframe>`。这挡住了**点击劫持**：攻击者把你真实的（不可见的）页面覆盖在诱饵之上，诱骗用户点击他们看不见的按钮。
- `X-Content-Type-Options: nosniff`——当声明的 `Content-Type` 看起来不对时，阻止浏览器猜测（「嗅探」）资源的类型。嗅探可能被诱骗把一张上传的图片当作脚本执行——经典的 **MIME 嗅探攻击**——这个请求头把它关掉。
- 带 `HttpOnly` 和 `Secure` 的 `Set-Cookie`——`HttpOnly` 对 JavaScript 隐藏 Cookie（这样一次成功的 XSS 也偷不走会话），`Secure` 确保它只通过 HTTPS 发送（这样它不会经明文泄露）。

第二部分 / 方法与语义

## HTTP 方法：深入剖析

方法（又称_动词_）表达请求的**语义意图**——它们告诉服务器你想要哪种动作，与 URL 无关。RFC 9110 定义了九个。每个都携带三个独立的属性，把它们搞对，就是一个正确、可安全重试、对缓存友好的 API 和一个满是 bug 的 API 之间的分水岭。

### 三个属性，精确定义

- **安全（Safe）**：请求是只读的；发出它不得改变可观测的服务器状态。要点在于，自动化代理——搜索爬虫、链接预取器、杀毒软件的 URL 扫描器——可以随意发出安全请求。如果一个 GET 删除了东西，爬虫会毁掉你的数据。（记录请求日志或给浏览计数器加一是被容忍的；_客户端所作用的资源_不得改变。）
- **幂等（Idempotent）**：N 个相同请求的_效果_等于一个请求的效果。正是这个性质让请求在网络故障后**可以安全重试**：如果你的客户端超时了、不确定请求是否到达，它可以重新发送而不用担心效果翻倍。关键在于，幂等性关乎_服务器状态_，而不是响应体——两个 DELETE 可能先后返回 200 和 404，但最终状态（「资源不存在了」）是相同的，所以 DELETE 是幂等的。
- **可缓存（Cacheable）**：响应可以被缓存（浏览器、CDN、代理）存储，并复用来回答之后的等价请求，而无需联系源服务器——省掉一次往返和一份负载。

<Callout type="info" title="属性之间的关系">
每个**安全**方法自动是**幂等**的：如果一个请求什么都不改变，做两次仍然什么都不改变。反过来不成立：PUT 和 DELETE 是幂等的但_不_安全，因为它们确实改变状态——只是确定性地改变，无论重复多少次，最终结果都一样。
</Callout>

### 权威属性表（RFC 9110）

| 方法    | 安全 | 幂等 | 可缓存   | 请求体 | 响应体 |
| ------- | ---- | ---- | -------- | ------ | ------ |
| GET     | 是   | 是   | 是       | 无     | 有     |
| HEAD    | 是   | 是   | 是       | 无     | 无     |
| OPTIONS | 是   | 是   | 否       | 无     | 有     |
| TRACE   | 是   | 是   | 否       | 无     | 有     |
| PUT     | 否   | 是   | 否       | 有     | 可选   |
| DELETE  | 否   | 是   | 否       | 可选   | 可选   |
| POST    | 否   | 否   | 有条件\* | 有     | 有     |
| PATCH   | 否   | 否   | 有条件\* | 有     | 可选   |
| CONNECT | 否   | 否   | 否       | 无     | 有     |

\*POST 和 PATCH 仅当响应显式包含新鲜度信息和匹配的 `Content-Location` 时才可缓存——实践中很罕见，所以把它们当作实际上不可缓存。

GET**获取资源的表示** 安全幂等可缓存

「把这个资源给我。」读取路径上的主力军。

GET 应该**只获取**数据，消息体不携带语义——大多数服务器、代理和缓存会忽略或拒绝 GET 的消息体，所以任何输入都必须放进 URL。过滤、排序和分页因此都住在**查询字符串**里（`/notes?done=false&sort=created&limit=20`），绝不放在消息体里。因为 GET 安全且可缓存，它的响应可以在每一层被存储——浏览器缓存、CDN、企业代理——这正是 Web 性能的引擎。这也正是为什么状态变更_绝不能_藏在 GET 后面：预取器、爬虫或缓存预热会触发它，在用户从未点击的情况下引发变更。

#### 后端行为

- 找到 -> 200 OK，资源在消息体中。
- 缺失 -> 404 Not Found。
- 客户端的缓存副本仍然有效 -> 304 Not Modified，空消息体（第 12 节）。

HEAD**类似 GET，但只有请求头，没有消息体** 安全幂等可缓存

「把你会为 GET 发送的元数据给我，但跳过载荷。」

服务器返回与 GET 完全相同的状态和请求头，包括 `Content-Length`、`Content-Type`、`ETag` 和 `Last-Modified`，但完全省略消息体。当你想要元数据而不想为下载付费时，这很有用：**检查资源是否存在**（200 对 404）、在决定获取之前读取文件大小、验证缓存副本的新鲜度，或者对一个 URL 做廉价的健康检查。大多数框架通过把 HEAD 路由到 GET 处理器并丢弃生成的消息体来自动实现它，这就是你很少单独写 HEAD 处理器的原因。

POST**提交数据；创建资源或触发处理** 不安全不幂等有条件可缓存

「这里有些数据，用它做点改变状态的事。」

POST 是通用的状态变更动词：创建记录、提交表单、启动后台任务、处理支付——任何不适合更具体动词的事。它决定性的（也是危险的）特征是**不幂等**：两个相同的 POST 会创建两个资源。这就是用户双击「购买」时产生重复订单的机制，也是不稳定的网络让客户端重试一笔不确定是否成功的支付时产生重复扣款的机制。解法是**幂等键**（第 7 节）——本质上就是给一个缺乏幂等性的方法接上幂等性。

#### 后端行为

- 创建了资源 -> 201 Created，最好带一个指向新 URL 的 `Location` 头，让客户端知道它现在住在哪里。
- 已接受进行异步处理（尚未完成）-> 202 Accepted。
- 校验失败 -> 400（请求格式错误）或 422（格式良好但语义无效）。
- 业务规则冲突，例如用户名重复 -> 409 Conflict。

PUT**用消息体整体替换目标资源** 不安全幂等不可缓存

「让这个 URL 上的资源看起来和这个消息体一模一样。」

PUT 执行**完全替换**：客户端提供资源的完整新表示，并指向一个_具体的_、已知的 URL（通常是客户端自己选的，比如 `/users/alice/avatar`）。这正是它幂等的原因——把同一个完整消息体发十次，每次资源都停在相同的最终状态，因为每个请求都是覆盖而不是累积。如果资源还不存在，PUT 也可以创建它（此时返回 201 Created），或者替换已存在的资源（此时返回 200 OK 或 204 No Content）。

用 PUT 还是 POST 创建

当由_服务器_决定新资源的身份时用 **POST**：`POST /notes`，服务器回复 `Location: /notes/42`。当_客户端_已经知道完整的目标 URL 时用 **PUT**：`PUT /users/alice/settings`。实际后果：用 PUT 创建是幂等的（可安全重试），用 POST 创建不是（重试可能产生重复）。选对动词，就是选择重试是否安全。

PATCH**对资源应用部分修改** 不安全不幂等\*有条件可缓存

「只改这些字段；其他一切别动。」

PUT 替换整个资源，而 PATCH 只发送**一组变更**：例如 `{"done": true}`，只翻转一个字段而无需重发整个对象。这更高效，也避免意外抹掉你没打算碰的字段。规范_不保证_ PATCH 幂等（表中的 \*）：像「把这项追加到列表」或「把计数器加 1」这样的补丁，每次运行都会产生不同的结果。一个把字段_设为_固定值的补丁在实践中通常是幂等的，但你不能普遍依赖它。服务器通过 `Accept-Patch` 响应头声明它接受哪些补丁文档格式，比如 JSON Merge Patch 或更精细的 JSON Patch。

<Callout type="info" title="经验法则">
部分更新用 **PATCH**，整体替换用 **PUT**。许多开发者在本意是 PATCH 时伸手用了 PUT（然后不得不发送每个字段以避免把它们清空）。除非你确实打算覆盖整个资源，否则默认用 PATCH。
</Callout>

DELETE**移除目标资源** 不安全幂等不可缓存

「删除这个资源。」

DELETE 幂等的原因微妙但重要：删除一次会移除资源，再删一次什么都不改变，因为它已经没了。各次尝试的_响应_可能不同（第一次返回 200/204，重复删除返回 404），但_服务器的状态_——「这个资源不存在」——在调用一次或十次之后是相同的。这种状态等价正是幂等的含义，这就是为什么客户端可以安全地重试一个超时了的 DELETE。没什么可返回时返回 204 No Content，或者返回 200 并在消息体中描述被删除的内容。

OPTIONS**描述目标的通信选项** 安全幂等不可缓存

「我能对这个资源做什么？」

OPTIONS 在不作用于资源的情况下，询问服务器它支持哪些方法和请求头；服务器用 `Allow` 头回答（如 `Allow: GET, POST, OPTIONS`）。它在现实世界中的主角戏份是 **CORS 预检**（第 9 节）：浏览器在发送「非简单」的跨源请求之前，会自动发出一个 OPTIONS 来请求许可，只有当服务器的响应批准了方法、请求头和源，才会继续。你几乎永远不会手动调用 OPTIONS，但你会在浏览器的 Network 面板里不断看到它和你的真实请求成对出现。

CONNECT**通过代理建立隧道** 不安全不幂等不可缓存

「代理，通过你打开一条到这个主机的原始双向隧道。」

CONNECT 几乎只被**处理 HTTPS 的正向代理**使用。当配置为使用代理的浏览器想要访问一个 HTTPS 站点时，它向代理发送 `CONNECT example.com:443`，代理打开一条到目标的 TCP 隧道，然后盲目地在两个方向转发加密的字节。因为隧道内的流量是端到端 TLS 加密的，代理无法读取或修改它——它只是铲字节。你基本上永远不会在应用服务器中实现 CONNECT；它活在代理和基础设施软件里（第 18 节）。

TRACE**沿请求路径的回环诊断** 安全幂等不可缓存

「把我发出去的请求回显回来，让我看看中间方改了什么。」

TRACE 要求服务器回显它收到的请求，这样客户端就能确切看到沿途的代理和网关如何修改了消息——一个针对请求链的调试工具。实践中它**几乎在所有地方都被禁用**，因为它助长了一类叫跨站追踪（XST）的攻击，可能把原本隐藏的请求头（比如 Cookie）暴露给恶意脚本。大多数服务器和框架直接拒绝 TRACE。为完整性起见知道它存在即可；你不会用到它。

## 实践中的幂等性

幂等性是让请求**可以安全重试**的性质——而重试在分布式系统中不是可选项，而是必然。网络会丢包，客户端超时了却不知道请求是否到达服务器，用户不耐烦地双击，移动应用在网络重连时重新发送。GET、PUT 和 DELETE 在设计上就是幂等的，所以重试它们无害。POST 不是——这就是重复记录和重复扣款 bug 的根源。

更深层的问题是**「结果未知」问题**：当客户端发出一个 POST，而连接在响应到达之前断开，客户端真的无法判断服务器是否处理了它。重试可能产生重复；不重试可能丢失这次操作。幂等键干净利落地解决了这个两难。

解法：幂等键

客户端为这次_逻辑操作_生成一个唯一键（通常是 UUID），并把它作为 `Idempotency-Key` 请求头发送。服务器把这个键和第一次成功执行的结果一起存储。如果同一个键再次到达——因为客户端重试了——服务器认出它，直接返回**存储的结果**而不重新执行。于是无论提交多少次，这个操作都_最多执行一次_。（MDN 现在把 `Idempotency-Key` 记录为正在标准化的请求头，Stripe 等支付 API 推广了这个模式。）

<Steps>
<Step>
客户端发送 `POST /payments`，携带 `Idempotency-Key: 9f8c-...`。
</Step>
<Step>
服务器检查键存储。键未见过 -> 执行扣款，持久化 `键 -> 结果`，返回 201。
</Step>
<Step>
网络把响应弄丢了。客户端不确定，用_同一个_键重试。
</Step>
<Step>
服务器看到键已存在 -> 返回存储的结果。**没有第二次扣款。**
</Step>
</Steps>

#### 实现注意事项

- **持久化存储键**：下面的内存 map 仅作演示；生产环境用 Redis 或数据库表，这样键能在重启后存活，并在所有服务器实例间共享（记住，任何节点都可能收到重试，第 1 节）。
- **给键一个 TTL**：比如 24 小时后让存储的键过期，这样存储不会无限增长。
- **先持久化再响应**：在发送结果之前记录它，这样在「做完了工作」和「存好了键」之间崩溃也不会丢失去重保证。

## Cookie、会话与认证

HTTP 是无状态的（第 1 节），但每个真实的应用都需要知道「这个请求和上一个请求来自同一个已登录用户」。协议不提供记忆，所以我们让客户端重新发送一小段凭证，在每个请求上重建身份。有两种主流架构，但它们都从同一个原语出发：Cookie。

### Cookie 在机制上如何工作

整个 Cookie 机制就是两个请求头。服务器在响应上附加一个 `Set-Cookie` 头；浏览器存储这个值，然后在之后发往该域名的每个请求中**自动**把它包含在 `Cookie` 头里——页面上没有任何代码要求它这样做。这种自动性既是便利（会话「就是能用」），也是危险（它正是 CSRF 成为可能的原因，见下面的 `SameSite`）。

```text title="Cookie 往返"
# 服务器的响应，设置一次 Cookie
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600; Path=/

# 浏览器之后的每个请求，自动携带
Cookie: session=abc123
```

#### 这些属性，以及每个对安全的意义

- `HttpOnly`——Cookie 对 JavaScript 不可见（`document.cookie` 读不到它）。这意味着即使一次成功的 XSS 注入也无法偷走会话令牌。
- `Secure`——Cookie 只通过 HTTPS 传输，因此不会经攻击者正在嗅探的明文连接泄露。
- `SameSite`——控制 Cookie 是否随跨站请求一起发送，这是防御 **CSRF（跨站请求伪造）** 的核心。`Strict` 从不在跨站时发送；`Lax`（现代默认值）在顶层导航时发送，但跨站子请求不发送；`None` 总是发送，但此时要求 `Secure`。
- `Max-Age` / `Expires`——生命周期；没有它们，Cookie 就是「会话 Cookie」，浏览器关闭即失效。`Domain` / `Path`——限定哪些主机和 URL 路径会收到它。

### 两种认证架构

两者之间的选择本质上是「会话状态住在哪里？」，而这个选择会传导到可扩展性和吊销能力上。

|               | 会话 Cookie（有状态）                            | 令牌 / JWT（无状态）                                                       |
| ------------- | ------------------------------------------------ | -------------------------------------------------------------------------- |
| 状态住在哪里  | 服务器存储完整会话；Cookie 只保存一个不透明的 ID | 客户端持有包含声明的签名令牌；服务器什么都不存                             |
| 通过什么发送  | `Cookie` 头（自动）                              | `Authorization: Bearer <token>`（由客户端显式设置）                        |
| 验证请求      | 每个请求都去存储里查会话 ID                      | 在本地验证密码学签名，无需查询                                             |
| 水平扩展      | 需要所有节点都能访问的共享会话存储（如 Redis）   | 轻而易举——任何节点都能验证签名，无需共享状态                               |
| 吊销          | 容易——在服务器端删除会话即可                     | 困难——令牌在过期前一直有效；需要黑名单，或短生命周期 + 刷新令牌            |

一个 **JWT** 是用点连接的三段 base64url：`header.payload.signature`。头部指明算法，载荷保存声明（用户 ID、过期时间），签名则用密钥或私钥对前两段计算得出。任何人都能_读_ JWT（它没有加密，只是编码了），但只有持有密钥的人才能_伪造_出有效签名——这正是服务器无需查数据库就能信任它的原因。常见的改进是短期访问令牌加长期刷新令牌，以缓解吊销上的弱点。

### JWT 如何防篡改（编码 vs. 加密）

一个常见的困惑点：JWT 的头部和载荷只是 **base64url 编码**，没有加密。任何截获令牌的人都能解码它、以明文读出声明，包括 `"role": "user"` 这样的字段。那么攻击者为什么不能直接解码、把角色改成 `"admin"`、再把改过的令牌发回来？

答案在第三段：**签名**。它是用一把从不离开服务器的密钥计算的 `HMAC(header + payload, secret)`（或私钥等价物）。当被篡改的令牌回来时，服务器用同一把密钥对（现在已经不同的）载荷重新计算签名；因为载荷变了，算出的哈希与令牌上附带的那个完全不同。比较失败，服务器以 401 拒绝请求——被修改的声明从未被信任。

编码不是加密

绝不要把秘密放进 JWT 载荷——任何人都能读它。签名只保证载荷在签发后没有被_改动_，不保证它是机密的。没有服务器的密钥，为修改过的载荷伪造有效签名在计算上不可行。

在协议层面，`WWW-Authenticate` 响应头（与 401 配对）告诉客户端该用哪种认证方案，而 `Authorization` 是把凭证带回来的请求头。

## CORS 与预检工作流

要理解 CORS，先得理解它所放松的那条规则。浏览器强制执行**同源策略**：来自某个源的页面上的 JavaScript，不得读取来自_不同_源的响应。「源」是 **协议 + 主机 + 端口** 的三元组：`https://example.com`、`https://example.com:8443` 和 `http://example.com` 都是不同的源。这条策略存在的原因是浏览器会自动把你的 Cookie 附加到请求上（第 8 节）；没有它，你访问的恶意网站就能悄悄地向你的银行 API 发出已认证的请求并读取响应。**CORS**（跨源资源共享）是服务器_主动选择_让特定其他源读取其响应的受控机制。

<Callout type="info" title="关键的框架">
CORS 完全由**浏览器**执行，而不是服务器。服务器只是通过响应头_声明_它允许谁；浏览器才是检查这些头、并决定是把响应交还给页面的 JavaScript 还是拦下它的那一方。这就是为什么 CORS 错误出现在浏览器控制台里，而服务器日志却显示一个完全正常的 200——请求_成功了_，只是浏览器拒绝分享结果。这也是为什么 `curl`、移动应用和服务器间调用完全无视 CORS：没有浏览器来执行它。
</Callout>

### 流程 1：简单请求

对于规范认定为「简单」的请求——只使用标准请求头和常见内容类型的 GET、POST 或 HEAD——浏览器懒得事先请求许可。它直接发送请求（带一个 `Origin` 头），事后再检查响应。

<Steps>
<Step>
浏览器自动加上 `Origin: https://example.com` 并发送请求。
</Step>
<Step>
服务器根据自己的策略检查这个源；如果允许，就在响应中包含回显该源（或 `*`）的 `Access-Control-Allow-Origin`。
</Step>
<Step>
浏览器看到匹配的头 -> 把响应交给页面。头缺失 -> 浏览器**拦截响应**并记录 CORS 错误——即使服务器已经处理了请求。
</Step>
</Steps>

### 流程 2：预检请求

对于任何更有风险的操作，浏览器会先发送一个预备的「可以吗？」请求。只要_任意一个_条件成立，就会触发**预检**：

- 方法不是 GET / POST / HEAD（所以 PUT、PATCH、DELETE 总是触发预检）。
- 请求携带非简单头——最常见的是 `Authorization` 或任何自定义 `X-` 头。
- `Content-Type` 在简单集合之外——而 `application/json` 就在集合之外。

为什么你到处都能看到 OPTIONS

由于一个典型的已认证 JSON API 请求会命中_全部三个_触发条件（JSON 消息体、Authorization 头、通常还是非 GET 方法），**几乎每个真实的 API 调用都会预检**。这就是为什么你的 Network 面板会在每个实际调用之前紧跟着显示一个配对的 `OPTIONS` 请求——那不是 bug，是浏览器在请求许可。

<Steps>
<Step>
浏览器发送 `OPTIONS /resource`，携带 `Access-Control-Request-Method` 和 `-Request-Headers`，询问「我可以从我的源用这个方法、这些头发送请求吗？」——没有消息体。
</Step>
<Step>
服务器回复 204 No Content，携带 `Access-Control-Allow-Origin / -Methods / -Headers`，外加 `-Max-Age` 告诉浏览器这份批准可以缓存多久（比如 24 小时），这样将来相同的调用就可以跳过预检。
</Step>
<Step>
批准通过 -> 浏览器发送真正的请求，并把真实的响应返回给页面。
</Step>
</Steps>

**携带凭证**的请求（带 Cookie 的那些）还有一个额外的弯子：服务器还必须发送 `Access-Control-Allow-Credentials: true`，并且在这种模式下，源_不能_用 `*` 通配符——必须指明确切的源。这防止服务器意外地把已认证的数据暴露给任意站点。

```go
func cors(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        h := w.Header()
        h.Set("Access-Control-Allow-Origin", "https://example.com") // 确切的源，不是 *（携带凭证时）
        h.Set("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE")
        h.Set("Access-Control-Allow-Headers", "Content-Type, Authorization")
        h.Set("Access-Control-Allow-Credentials", "true")
        h.Set("Access-Control-Max-Age", "86400") // 把批准缓存 24 小时
        if r.Method == http.MethodOptions {
            w.WriteHeader(http.StatusNoContent)  // 204：回答预检，然后停止
            return
        }
        next.ServeHTTP(w, r)
    })
}
```

### 常见误解：CORS 保护的是服务器吗？

一个常见的问题是：「如果脚本用 `curl` 或自定义 HTTP 客户端就能无视 CORS，那 CORS 对安全岂不是没用？」前提是对的——CORS 在浏览器之外绕过它轻而易举——但结论是错的，因为 **CORS 从来不是设计来保护服务器的；它保护的是用户**。

当 `curl` 或自定义脚本这样的工具无视 CORS 时，它可以读取服务器返回的任何东西，但它没有用户的 Cookie 或会话令牌，所以服务器只会以未认证拒绝它（第 8 节）。CORS 其实是在_正当的浏览器_内部执行同源策略：如果用户登录了自己的银行，然后访问了一个恶意站点，那个站点的 JavaScript 运行在用户自己的浏览器里，浏览器会自动把银行的会话 Cookie 附加到它发出的任何请求上。CORS 就是浏览器向银行询问「这个恶意源有权限读取这个响应吗？」的机制——答案是否定时，就拦截响应。

谁保护什么

服务器通过认证、授权和 CSRF 令牌保护自己。CORS 保护用户那个已被信任的、携带 Cookie 的会话，不被一个它从未同意与之共享的源读取。

#### 恶意扩展的威胁

恶意浏览器扩展会彻底打破这条信任链：它运行在_受信任的浏览器内部_，与页面并肩，所以它能绕过 CORS、直接读取 Cookie、记录按键，并在请求到达网络之前改写它们。保护客户端环境和保护后端同等重要——没有任何服务器端请求头能阻止已经运行在你 Cookie 所在之处的代码。

## 状态码

401 对 403——最常见的混淆

**401 Unauthorized** 实际意思是_未认证_——「我不知道你是谁；把凭证发来。」**403 Forbidden** 意思是_已认证但未授权_——「我清楚你是谁，但你就是不被允许。」一个已登录用户访问仅限管理员的端点，得到的是 403，不是 401。用对名字，客户端才能正确反应：401 -> 显示登录界面；403 -> 显示「拒绝访问」。

<Callout type="info" title="400 对 422">
**400** 用于服务器连解析都解析不了的请求——坏掉的 JSON、畸形的编码。**422** 用于解析完全正常但语义上无效的请求——一个格式良好的 JSON 对象，其 `email` 字段里却是个电话号码。FastAPI 对自动校验失败返回 422；许多 API 两者都用 400，但这个区分能帮客户端分清「修你的语法」和「修你的数据」。
</Callout>

<Callout type="info" title="5xx 与代理三兄弟">
5xx 意味着服务器未能完成一个有效请求，所以你日志里的 500 是_你的_ bug，不是客户端的。但 **502 / 503 / 504** 很特殊：你几乎不会从应用代码里发出它们。它们由**挡在你前面的代理或负载均衡器**（nginx、Envoy、云厂商的 LB）生成——当它联系不上你的应用、发现它宕了，或者等太久了。看到它们，指向的是基础设施和上游健康，而不是你的处理器逻辑——一个至关重要的分诊捷径。
</Callout>

```go
func getUser(w http.ResponseWriter, r *http.Request) {
    if r.Header.Get("Authorization") == "" {
        http.Error(w, "login required", http.StatusUnauthorized) // 401：你是谁？
        return
    }
    user, err := db.Find(r.PathValue("id"))
    if err == ErrNotFound {
        http.Error(w, "no such user", http.StatusNotFound)       // 404
        return
    }
    if !user.VisibleTo(r) {
        http.Error(w, "forbidden", http.StatusForbidden)         // 403：没有权限
        return
    }
    json.NewEncoder(w).Encode(user)                              // 200
}
```

## 重定向

重定向让一个资源可以住在多个 URL 上：服务器用 `3xx` 状态和一个指明去向的 `Location` 头响应，客户端（自动跟随的浏览器，或你的 HTTP 库）向那个新 URL 重新发出请求。重定向支撑着 URL 迁移、规范 URL 强制、HTTP->HTTPS 升级，以及 Post/Redirect/Get 模式。让后端栽跟头的细节是**原始方法和消息体能否在重定向后存活**——因为历史上它们常常不能。

| 状态码                 | 永久？ | 方法保留？                                  | 使用场景                                                                                                  |
| ---------------------- | ------ | ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 301 Moved Permanently  | 是     | 不保证（客户端可能把 POST 变成 GET）        | 资源永久迁移——更新书签，转移 SEO 权重。                                                                   |
| 302 Found              | 否     | 不保证（客户端可能把 POST 变成 GET）        | 临时搬迁；继续使用原 URL。                                                                                |
| 303 See Other          | 否     | 强制变成 GET                                | Post/Redirect/Get——POST 之后重定向到结果页，这样浏览器刷新不会重新提交表单。                              |
| 307 Temporary Redirect | 否     | **是**：方法与消息体保留                    | 临时重定向，且必须以消息体完整地重新发出同一个 POST/PUT。                                                 |
| 308 Permanent Redirect | 是     | **是**：方法与消息体保留                    | 必须保留 POST/PUT 的永久迁移。                                                                            |

解释 307/308 由来的历史陷阱

早期客户端面对 POST 上的 301 或 302 时，会静默地把它重新发成 **GET 并丢弃消息体**——技术上违反规范，但太普遍了，以至于成了预期行为。这种含糊（「我的 POST 能在这次重定向后存活吗？」）正是 **307** 和 **308** 被创造出来的原因：它们_保证_方法和消息体被保留。所以，如果一个被重定向的表单提交神秘地空着数据到达，那就是你在该用 308/307 的地方用了 301/302。反过来，303 故意强制变成 GET——这正是 Post/Redirect/Get 想要的，这样用户就能安全地刷新结果页。

## HTTP 缓存

缓存就是存一份响应的副本，好让之后的请求无需从源站重新获取就能被满足——同时削减带宽、延迟和服务器负载。它可以说是 Web 性能最大的单一杠杆。HTTP 缓存运行在**两个不同的层**上，把它们混为一谈是常见的困惑来源：

- **新鲜度**：「我能_问都不问_就复用我的副本吗？」如果响应还新鲜，客户端直接从缓存提供它，零网络调用。
- **验证**：「我的副本可能过期了；它_真的变了吗_？」这是一次廉价的往返，返回的要么是「没变，继续用你的」，要么是新内容。

缓存还住在多个**层级**上：私有的浏览器缓存（只服务一个用户），以及 CDN 和反向代理这样的共享缓存（服务许多用户）。下面的 `Cache-Control` 指令决定哪些层级可以存储一个响应。

### 第 1 层：通过 `Cache-Control` 控制新鲜度

服务器给响应盖上它能用多久的戳，这样客户端在那之前可以自由复用它：

- `max-age=3600`——新鲜一小时；过期之前无需网络即可复用。
- `public` 对 `private`——_共享_缓存（CDN/代理）可以存它，还是只有用户自己的浏览器可以？个性化或已认证的响应用 `private`，这样 CDN 不会把一个用户的数据发给另一个用户。
- `no-cache`——反直觉的是，它的意思是「你可以存，但每次使用前必须向源站_重新验证_」。它是「总是检查」，不是「永不缓存」。
- `no-store`——真正的「任何地方都别缓存」指令，用于敏感数据。
- `immutable`——「这东西在新鲜期内永远不会变，所以连重新验证都别做。」非常适合内容哈希过的静态资源（`app.4f9a2c.js`）——反正一变就会产生新文件名。

### 第 2 层：通过 `ETag` 和 `Last-Modified` 验证

新鲜度失效后，客户端不会盲目地重新下载——它会重新验证。原始响应携带一个 `ETag`（内容的指纹/哈希）和/或一个 `Last-Modified` 时间戳。客户端把它们作为_条件_头发送回去，如果什么都没变，服务器返回一个没有消息体的微小 304——省下了整个载荷。

<Steps>
<Step>
第一次 GET -> 200 + 消息体 + `ETag: "abc"` + `Cache-Control: max-age=10`。
</Step>
<Step>
新鲜度过期后，下一个 GET 发送 `If-None-Match: "abc"`（和/或 `If-Modified-Since`）。
</Step>
</Steps>
<StepBranch labelA="3a" labelB="3b">
<Fragment slot="a">
没变 -> 304 Not Modified，空消息体。客户端复用自己的副本；载荷字节全省了。
</Fragment>
<Fragment slot="b">

</Fragment>
</StepBranch>

ETag 有两种口味：**强** ETag（`"abc"`）保证逐字节一致，而**弱** ETag（`W/"abc"`）只承诺语义等价——比如响应里的时间戳不同但有意义的内容没变时，就很有用。

Go Python JavaScript

```go
func getResource(w http.ResponseWriter, r *http.Request) {
    body := loadResource()
    sum := sha256.Sum256(body)
    etag := `"` + hex.EncodeToString(sum[:8]) + `"`  // 内容的指纹

    if r.Header.Get("If-None-Match") == etag {  // 客户端已经有这个确切的版本
        w.WriteHeader(http.StatusNotModified)   // 304，无消息体，载荷省了
        return
    }
    w.Header().Set("ETag", etag)
    w.Header().Set("Cache-Control", "max-age=10")
    w.Write(body)                               // 200 + 消息体
}
```

```python
import hashlib
from fastapi import Request, Response

@app.get("/resource")
def get_resource(request: Request):
    body = load_resource()
    etag = '"' + hashlib.sha256(body).hexdigest()[:16] + '"'  # 指纹

    if request.headers.get("if-none-match") == etag:   # 已经缓存了
        return Response(status_code=304)               # 304，无消息体，载荷省了

    return Response(content=body, status_code=200,
                    headers={"ETag": etag, "Cache-Control": "max-age=10"})
```

```js
import { createHash } from 'node:crypto'

app.get('/resource', (req, res) => {
  const body = loadResource()
  const etag = `"${createHash('sha256').update(body).digest('hex').slice(0, 16)}"`

  if (req.get('If-None-Match') === etag) {  // 客户端已经有这个确切的版本
    return res.status(304).end()            // 304，无消息体，载荷省了
  }
  res.set('ETag', etag)
  res.set('Cache-Control', 'max-age=10')
  res.send(body)                            // 200 + 消息体
})
```

<Callout type="info" title="实践中 + Vary 陷阱">
手工管理 ETag 容易出错——改内容时忘了更新它，客户端就会无限期地提供过期数据。静态资源优先用 `immutable` + 内容哈希文件名；API 数据用 React Query 这类客户端缓存能获得更细的控制。还有别忘了 `Vary`：它告诉缓存哪些_请求_头会让响应不同（如 `Vary: Accept-Encoding`）。漏掉它，共享缓存可能把 gzip 压缩过的消息体发给没要求压缩的客户端，或者把法语响应递给说英语的人。
</Callout>

## 条件请求与乐观锁

驱动缓存的同一组验证器（第 12 节）还解决了第二个更深层后端问题：**丢失更新**。想象两个编辑同时打开文档 v1。Alice 保存了她的修改；Bob 还在基于 v1 工作，过了一会儿也保存了——Bob 的保存静默地覆盖了 Alice 的，没有错误，没有警告。她的工作就这样消失了。条件请求通过**乐观并发控制**防止这种情况：不是在有人编辑时锁住资源（悲观），而是让所有人自由编辑，只在_保存的那一刻_检测冲突。

### 条件请求头

每一个都在说「仅当关于资源当前版本的某个条件成立时才继续」。命名是对称的：`If-None-Match` 用于读（变了才继续 -> 我需要新副本），`If-Match` 用于写（没变才继续 -> 覆盖是安全的）。

| 请求头              | 仅当……才继续                                       | 典型用途                                           |
| ------------------- | -------------------------------------------------- | -------------------------------------------------- |
| If-None-Match       | ……ETag _不_匹配（资源变了）                        | GET 上的缓存 -> 没变时返回 304                     |
| If-Match            | ……ETag 匹配（自我读取以来没变）                    | PUT/PATCH/DELETE 上的安全写入 -> 冲突时返回 412    |
| If-Modified-Since   | ……它在这个时间戳之后变了                           | 没有 ETag 时的缓存兜底                             |
| If-Unmodified-Since | ……它自这个时间戳以来_没_变                         | 基于时间戳的安全写入                               |
| If-Range            | ……资源没变（否则发送完整内容）                     | 可续传的下载（第 15 节）                           |

</Fragment>

为什么这胜过数据库锁

悲观锁会在用户盯着编辑表单的整段时间里——可能几分钟——一直锁住一行，阻塞其他所有人，而且如果用户走开了还有死锁风险。乐观并发_什么都不锁_：它让所有读者照常进行，只在写入的瞬间通过比较版本标签来廉价地检测冲突。代价是偶尔一次保存会失败、必须重试——这几乎总是更划算的交易。协作编辑器、维基和设计良好的 REST API 就是这样防止静默覆盖的。

## 内容协商与压缩

一个 URL 可以有多个**表示**：同一篇文章可以是 HTML 或 JSON，可以是中文或英文，可以压缩或不压缩。内容协商是客户端和服务器就最佳表示达成一致的机制。主流形式是**服务器驱动（主动）**协商：客户端在 `Accept*` 请求头里列出自己的偏好，服务器挑出它能产生的最佳匹配，并在对应的 `Content-*` 响应头里表明自己的选择。（还有_代理驱动_协商——服务器返回一个选项列表让客户端挑——但很少用。）

偏好可以用 0 到 1 的质量值**加权**：`Accept: application/json;q=1.0, text/html;q=0.8, */*;q=0.1` 读作「强烈偏好 JSON，接受 HTML，万不得已什么都行」。服务器满足它能产生的、权重最高的类型。如果它能满足的可接受类型_一个都没有_，正确的响应是 406 Not Acceptable，而不是静默返回错误的格式。

### 压缩：同一套协商，作用于体积

压缩就是编码协商。当客户端声明 `Accept-Encoding: gzip` 时，服务器可以在发送前压缩文本响应——在 JSON、HTML 和 JS 上的节省是惊人的，因为它们高度重复：一个约 26 MB 的 JSON 载荷可以缩到约 3.8 MB。服务器设置 `Content-Encoding: gzip`，浏览器透明地解压，两端的应用代码都毫无察觉。有两条规则要紧：只在客户端说过它能解码时才压缩（否则你发的是垃圾），以及**总是搭配 `Vary: Accept-Encoding`**，这样共享缓存不会把压缩过的消息体发给处理不了它的客户端（第 12 节）。

```go
func handler(w http.ResponseWriter, r *http.Request) {
    body, _ := json.Marshal(bigPayload)
    w.Header().Set("Content-Type", "application/json")
    w.Header().Set("Vary", "Accept-Encoding")   // 告诉缓存消息体随编码变化
    if strings.Contains(r.Header.Get("Accept-Encoding"), "gzip") {
        w.Header().Set("Content-Encoding", "gzip")
        gz := gzip.NewWriter(w)
        defer gz.Close()
        gz.Write(body)
        return
    }
    w.Write(body) // 给无法解码 gzip 的客户端的未压缩兜底
}
```

## 范围请求

**范围请求**只请求资源的一个切片，而不是整个东西。它解决了三个真实的问题：**续传**一个在 80% 处失败的下载而无需从零开始；在音频/视频中**跳转**（跳到第 3 分钟只取它附近的字节）；以及把大下载**并行化**为同时获取的多个块。没有范围请求，每次中断都意味着从头再来，每次跳转都意味着把目标之前的一切全部下载。

### 这次交换，一步一步

- 服务器通过在普通响应上包含 `Accept-Ranges: bytes` 来表明它支持范围。
- 客户端用 `Range` 头请求一个切片：`Range: bytes=0-1023`（第一个千字节），或 `bytes=1024-`（从第 1024 字节到结尾——正是续传下载发送的东西）。
- 服务器回复 206 Partial Content，携带 `Content-Range: bytes 1024-50000/50001` 头（哪个切片，总共多大），消息体里只有那些字节。
- 如果请求的范围无效（比如起点超过了文件末尾），服务器返回 416 Range Not Satisfiable。
- 对于_续传_，文件可能在部分下载开始后就变了，所以客户端加上 `If-Range: "<etag>"`：服务器只在资源没变时才发送部分，否则返回完整的 200，让客户端干净地重新开始，而不是把不兼容的两半缝在一起。

```text title="范围交换 / 从第 1024 字节续传"
# 服务器只返回剩余的切片
```

## 持久连接与 Keep-Alive

建立 TCP 连接不是免费的——握手要花费整整一次往返（如果涉及 TLS 还要更多）。HTTP/1.0 在每个请求上都付一次这笔过路费，为每个资源打开又拆除一条连接，这让加载一个有几十个资源的页面慢得痛苦。HTTP/1.1 用**持久连接**修复了这一点：一条 TCP 连接保持打开，被许多请求/响应周期复用，握手成本只付一次，摊薄到之后的一切之上。

#### 机制与旋钮

- 在 HTTP/1.1 中，连接**默认就是持久的**：零配置就能获得好处。
- `Connection: keep-alive` 显式请求连接保持打开，`Keep-Alive` 头可以附加参数：_timeout_（空闲连接保持多久后关闭）和 _max_（服务多少个请求后关闭它）。
- `Connection: close` 要求在这个响应之后关闭连接——HTTP/1.0 的默认行为，在 1.1 中当你想要一次性交换时仍可设置。
- **管道化（Pipelining）**：不等每个响应就连着发好几个请求——在 1.1 中被规定，但它受队头阻塞之苦（第一个响应慢，这条连接上的其余全被堵住），而且各实现里 bug 太多，实际上已经死了。HTTP/2 多路复用（第 2 节）才是它正当的替代品。

<Callout type="info" title="这对你在哪里重要">
你很少手工设置这些头——默认值对几乎所有场景都是对的。持久连接真正需要操心的场合是**调服务器超时**：连接保持太久会泄漏空闲连接、在负载下耗尽连接池；关得太急又会失去延迟上的好处。下面的超时还兼任防御——读超时给得太慷慨，会让 Slowloris 攻击者通过一次一个字节地发请求头来占住连接。
</Callout>

### 大上传（客户端 -> 服务器）-> `multipart/form-data`

客户端把请求体拆成离散的**部分**：每个部分可以是一个表单字段或一个文件，由 `Content-Type` 的 `boundary` 参数声明的唯一分隔符字符串隔开。边界出现在每个部分之前，并在最后以带尾巴 `--` 的形式再出现一次，标记真正的结束。这让服务器可以流式解析请求体，逐个剥下每个部分（每个部分有自己的 `Content-Disposition` 命名它，以及可选的按部分的 `Content-Type`），而无需一次性把所有东西装进内存。唯一的边界让嵌入任意二进制字节变得安全——解析器扫描分隔符，而不是只依赖长度。

```text title="multipart 请求的形状"
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----X7gQ2

------X7gQ2
Content-Disposition: form-data; name="file"; filename="cat.png"
Content-Type: image/png

（二进制图片字节）
------X7gQ2--          # 结束边界标记终点
```

### 大下载（服务器 -> 客户端）-> 流式

要发送一个大的或开放式的响应而不把它全部缓冲在内存里（或者在构建它的时候超时），服务器把它**流式**地分片发送。两种相关的技术：`Transfer-Encoding: chunked` 在总大小事先未知时，把消息体作为一系列自描述的块发送（所以没有 `Content-Length`）；`Content-Type: text/event-stream` 实现 **Server-Sent Events**——一个长寿命的响应，服务器通过它把带标签的 `data:` 事件随发生随推送。连接靠 keep-alive 保持打开，客户端在每一块到达时追加它——非常适合进度更新、日志尾随，或逐 token 的 LLM 输出。

Go Python JavaScript

```go
// 1. 接收 multipart 上传
func upload(w http.ResponseWriter, r *http.Request) {
    r.ParseMultipartForm(32 << 20) // 内存中最多 32 MB，溢出部分落到磁盘
    file, header, err := r.FormFile("file")
    if err != nil {
        http.Error(w, "no file", http.StatusBadRequest)
        return
    }
    defer file.Close()
    fmt.Fprintf(w, "received %s", header.Filename)
}

// 2. 以块流式输出响应（Server-Sent Events）
func stream(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Connection", "keep-alive")
    flusher := w.(http.Flusher) // Flush() 把每一块立即推给客户端
    for i := 0; i < 5; i++ {
        fmt.Fprintf(w, "data: chunk %d\n\n", i)
        flusher.Flush()
        time.Sleep(time.Second)
    }
}
```

### 正向代理与反向代理：相反的两端

- **正向代理**坐在_客户端_前面，代表它们发出请求——想想企业出口网关、内容过滤器或匿名化工具。目标服务器看到的是代理，而不是用户。通过正向代理的 HTTPS 使用 `CONNECT` 方法（第 6 节）打开一条不透明的加密隧道。
- **反向代理**坐在_服务器_前面；客户端以为自己在直接和它说话。它挡在你的后端前面，处理 TLS 终止、负载均衡、缓存、压缩和基于路径的路由。你的代码就活在它后面——CDN 本质上就是一个全球分布的反向代理缓存。

### 后果：你失去了真实的客户端

一旦反向代理把请求转发给你的应用，你的处理器看到的 TCP 连接来自_代理的_ IP，而且（通常）走的是明文 HTTP——因为 TLS 在边缘被终止了。所以 `r.RemoteAddr` 是代理，协议看起来是 http，尽管用户用的是 https。为了保留原始信息，代理会注入转发头：

| 请求头            | 携带的内容                                                                  |
| ----------------- | --------------------------------------------------------------------------- |
| X-Forwarded-For   | 原始客户端 IP，加上它经过的代理链。                                         |
| X-Forwarded-Proto | 原始协议，`https`——即使代理->应用这一跳是明文 http。                        |
| X-Forwarded-Host  | 客户端最初请求的 `Host`。                                                   |
| Forwarded         | 标准化的单一请求头（RFC 7239），合并了上面这些。                            |
| Via               | 消息经过的代理/网关，用于环路检测和追踪。                                   |

两个咬到所有人的陷阱

**伪造：** `X-Forwarded-For` 只是一个客户端也能设置的请求头，所以如果你用它做限流、地理定位或审计日志，你必须只在请求来自_已知、可信的代理 IP_ 时才信任它——否则攻击者可以伪造任何他们喜欢的 IP。**错误协议的 URL：** 如果你用本地连接的协议（在代理后面是 http）而不是尊重 `X-Forwarded-Proto` 来构建绝对 URL 或重定向 URL，你会在 HTTPS 站点上生成 `http://` 链接，导致混合内容警告和重定向循环。大多数框架都带「可信代理」中间件，能根据这些头正确地改写 `RemoteAddr` 和协议——启用它，而不是裸读这些头。

## 协议升级与 WebSocket

HTTP 的请求/响应、客户端发起的形态，不适合那些需要_服务器_在事情发生的瞬间就推送数据的工作负载——实时通知、聊天、多人游戏状态、协作光标、交易行情。历史上这些用轮询（反复询问）或长轮询（把一个请求挂着）来伪装。HTTP/1.1 的**升级机制**提供了一条干净的出路：一条已建立的 HTTP 连接可以中途_切换协议_——最著名的就是切换成 WebSocket。

### WebSocket 握手

优雅之处在于它以普通的 HTTP 开始——所以它能穿过同样的端口和代理——然后升级：

- 客户端发送一个普通的 GET，携带 `Upgrade: websocket`、`Connection: Upgrade`、一个随机的 `Sec-WebSocket-Key` 和版本号。
- 服务器以 101 Switching Protocols 同意，并附上根据客户端的键计算出的 `Sec-WebSocket-Accept`（证明它理解了握手，而不只是回显）。
- 从那一刻起，这条 TCP 连接不再是 HTTP——它是一个持久的、**全双工**的 WebSocket，承载轻量的消息帧。任何一方都可以随时发送，没有逐消息的 HTTP 开销，也没有轮询。

```text title="升级握手"
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

<Callout type="info" title="选对工具">
不要条件反射地伸手拿 WebSocket。对于**单向**的服务器->客户端流——通知、进度条、日志尾随、流式 LLM token——**Server-Sent Events**（第 17 节）更简单：它们就是纯 HTTP，自动重连，不需要特殊协议。只有当你确实需要_双向_、低延迟的消息传递（聊天、游戏、协作编辑）时才用 **WebSocket**。而对于普通的请求/响应 API，两个都别用——带良好缓存的纯 HTTP 才是正确答案。
</Callout>

## SSL、TLS 与 HTTPS

这就是把 HTTP 变成 HTTPS 的那一层。你很少自己实现它，但你必须理解它保证什么、在哪里运行。

- **SSL**（安全套接层）——保护客户端-服务器通信的原始协议。由于被发现漏洞，它的所有版本现在都已_过时并被禁用_；这个名字只在口语中留存。
- **TLS**（传输层安全）——SSL 的现代继任者。它做两件事：加密**传输中**的数据，让窃听者读不到、篡改者无法悄悄改动；以及用**证书**认证服务器真的是它声称的那一方。当前推荐的版本是 TLS 1.3，既更快，又剥离了遗留的弱密码套件。
- **HTTPS**：就是承载在 TLS 连接里的 HTTP。协议相同，语义相同；本手册里的一切都原样适用，只是底下多了加密。

### 击败中间人（MitM）攻击

**中间人攻击**发生在有人坐在客户端和服务器之间的网络路径上——比如控制了一台公共 Wi-Fi 路由器——并截获流量时。在明文 HTTP 上，攻击者就像一个不诚实的邮递员：他们能读取传输中的密码、修改请求体、改写服务器的响应，而双方都以为自己在直接和对方说话。

**这正是 TLS 堵上的漏洞。** 一旦下面的握手完成，离开客户端的每个字节在碰到线缆之前就被封进了加密通道。在被攻破的网络上的攻击者仍然能看到流量——但他们看到的只是一串无法破译的密文，因为他们从未拿到握手期间协商出的会话密钥。没有那把钥匙，截获就毫无用处：什么都读不到，而且任何改动都会破坏接收方验证的完整性检查。

### 握手实际达成了什么

不沉溺于密码学细节，TLS 握手在任何 HTTP 流动之前确立三件事：

- **认证**：服务器出示一份由客户端已经信任的证书颁发机构（CA）签名的_证书_，以密码学方式证明它拥有 `example.com`。这正是阻止你连接到冒名顶替者的东西。（证书向上链到烘焙在你操作系统/浏览器里的一小组根 CA。）
- **密钥交换**：使用非对称（公钥）密码学，双方商定一个共享的_对称_会话密钥，而从不明文传输它。非对称加密很慢，所以只用于引导；快速的对称密钥才加密实际流量。
- **加密 + 完整性**：从那时起，每个字节都被加密并携带防篡改检查，攻击者既无法读取，也无法在不被发现的情况下修改对话。

一个值得知道的实用细节：**SNI**（服务器名称指示）是握手中客户端声明它想要哪个主机名的部分，这样一个服务多个 HTTPS 站点的 IP 就能出示正确的证书——`Host` 头在 TLS 层的对应物。

<Callout type="info" title="TLS 实际住在你技术栈的哪里">
你几乎从不在应用代码里实现 TLS。它在边缘被_终止_——由你的托管平台、负载均衡器或反向代理（nginx、Caddy、云厂商的 LB）——证书通常通过 Let's Encrypt 自动签发和续期。然后你的应用在那道边界之后接收明文 HTTP。这正是 `X-Forwarded-Proto`（第 18 节）重要的原因——它是你的应用得知用户在用 HTTPS 的方式——也是你在边缘设置 `Strict-Transport-Security`（第 5 节）来首先强制 HTTPS 的原因。
</Callout>

## 调试速查表

理解这些机制的回报是快速分诊：把一个症状直接映射到子系统和掌管它的请求头。

| 症状                                                     | 检查                                                                                                                                                                       |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 控制台里的 **CORS 错误**（但服务器日志显示 200）         | 对比 `Origin` 与 `Access-Control-Allow-Origin`；验证预检 `OPTIONS` 返回了正确的 `Allow-Methods/Headers`；带 Cookie 时检查 `Allow-Credentials` 且源不是 `*`。（第 9 节）    |
| 正在提供**过期数据**                                     | 检查 `Cache-Control`、`ETag`/`If-None-Match`、`Last-Modified`；ETag 是否在每次变更时都更新了？`Vary` 设对了吗？（第 12 节）                                                |
| **丢失更新** / 静默覆盖                                  | 加乐观锁：要求带 ETag 的 `If-Match`，不匹配就以 412 拒绝。（第 13 节）                                                                                                     |
| 重试时出现**重复记录**                                   | POST 不幂等——要求 `Idempotency-Key` 并据此去重。（第 7 节）                                                                                                                |
| **重定向的 POST 丢了消息体**                             | 你用了 301/302（客户端可能切换成 GET）；用 307/308 保留方法与消息体。（第 11 节）                                                                                          |
| **返回了错误的格式/语言**                                | 把 `Accept`、`Accept-Language`、`Accept-Encoding` 与服务器的 `Content-*` 对比；考虑 406。（第 14 节）                                                                      |
| **401 与 403 混淆**                                      | 401 = 未认证（发送凭证）；403 = 已认证但没有权限。（第 10 节）                                                                                                             |
| **400 与 422**                                           | 400 = 语法畸形；422 = 语法有效但业务校验失败。（第 10 节）                                                                                                                 |
| **502 / 503 / 504**                                      | 是基础设施，不是你的处理器——上游不可达 / 宕机 / 太慢。检查代理和上游健康。（第 10 节、第 18 节）                                                                           |
| **你设置的请求头没发出去**                               | 你在写状态码或消息体之后才设置它。永远先设置请求头。（第 3 节）                                                                                                            |
| **真实客户端 IP 显示成了代理**                           | 读 `X-Forwarded-For`，但只在请求来自可信代理时。（第 18 节）                                                                                                               |
| **HTTPS 站点生成了 http\:// 链接**                       | 用 `X-Forwarded-Proto` 而不是本地（被代理的）协议来构建绝对 URL。（第 18 节）                                                                                              |
| **负载下连接耗尽**                                       | 调整 keep-alive 空闲超时和连接数限制；用读请求头超时防范 Slowloris。（第 16 节）                                                                                           |

#### 值得记住的请求头，按职责分组

- **协商：** `Accept`、`Accept-Language`、`Accept-Encoding` &harr; `Content-Type`、`Content-Language`、`Content-Encoding`
- **表示：** `Content-Type`、`Content-Length`、`Content-Range`
- **身份 / 认证：** `Authorization`、`WWW-Authenticate`、`Cookie`、`Set-Cookie`、`Host`、`User-Agent`
- **缓存 / 条件：** `Cache-Control`、`ETag`、`Last-Modified`、`If-None-Match`、`If-Match`、`If-Modified-Since`、`Vary`
- **CORS：** `Origin`、`Access-Control-Allow-Origin / -Methods / -Headers / -Credentials / -Max-Age`
- **安全：** `Strict-Transport-Security`、`Content-Security-Policy`、`X-Frame-Options`、`X-Content-Type-Options`
- **代理：** `X-Forwarded-For / -Proto / -Host`、`Forwarded`、`Via`
- **连接 / 传输：** `Connection`、`Keep-Alive`、`Upgrade`、`Transfer-Encoding`、`Range`、`Accept-Ranges`

**一口气说完整个流程：** 客户端打开一条连接——可复用（第 16 节）、通常经 TLS 加密（第 20 节）、常常穿过一个反向代理（第 18 节）——然后发送一个自包含的请求（第 1 节）：一个带安全/幂等/可缓存语义的方法（第 6 节）、一个 URL、请求头（第 4-5 节），以及可选的消息体（第 3 节）。无状态的服务器重建身份（第 8 节），检查授权与前置条件（第 10 节、第 13 节），协商最佳表示（第 14 节），查阅缓存（第 12 节），执行工作，并返回一个带状态码的响应（第 10 节）——可能是重定向（第 11 节）、部分范围（第 15 节）或流（第 17 节）。把这个闭环和引导每一步的请求头内化，你就能推理和调试今后遇到的绝大多数后端 HTTP。
